## Аннотация

Универсальные законы — это фундаментальные закономерности, которые проявляются во всех информационных системах независимо от их назначения, технологии реализации или масштаба. Эти законы находятся между философскими принципами (α=+3) и конкретными принципами проектирования (α=+1).

**Отличие от других уровней:**

- **Философия (α=+3):** «Почему это важно для человека?» — онтология, этика, забота
- **Универсальные законы (α=+2):** «Как это работает всегда?» — неизменные закономерности
- **Принципы (α=+1):** «Как это применять?» — SOLID, KISS, DRY и др.
- **Код (α=-4):** «Как это реализовано здесь?» — конкретная имплементация

## 1. Закон сохранения информации

### Формулировка

**Информация в системе не может быть уничтожена случайно — только преднамеренно.**

### Обоснование

Любая система, работающая с ценной информацией, должна гарантировать её сохранность. Потеря данных может произойти только в результате явного действия пользователя (удаление), но не в результате сбоя системы.

### Проявления

- **Персистентность:** Данные сохраняются на диск, а не только в памяти
- **Атомарность:** Операции выполняются полностью или не выполняются вовсе
- **Версионирование:** История изменений сохраняется (Git, backup)
- **Fail-safe:** При ошибке система не теряет данные

### Связь с философией (⇑)

Философия заботы (Sorge, α=+3): забота о том, чтобы важное не было потеряно.

### Реализация в коде (⇓)

```python
# card_manager.py
def save(self, card: Card):
    """Атомарное сохранение с защитой от потери данных"""
    file_path = self.cards_dir / f"{card.id}.md"
    temp_path = file_path.with_suffix('.tmp')

    # Сначала записать во временный файл
    temp_path.write_text(card.to_markdown(), encoding='utf-8')

    # Только потом атомарно заменить (rename atomic на POSIX)
    temp_path.replace(file_path)
```

**Принципы (α=+1):** Fail-Safe Design, Defensive Programming

## 2. Закон единственности источника истины

### Формулировка

**В системе существует ровно один источник истины для каждого факта.**

### Обоснование

Дублирование информации приводит к противоречиям: если один и тот же факт хранится в двух местах, эти копии могут рассинхронизироваться. Система должна иметь единственный источник истины (Single Source of Truth, SSOT).

### Проявления

- **Normalization:** В БД данные нормализуются, чтобы избежать дублирования
- **Reference by ID:** Вместо копирования объектов используются ссылки на ID
- **Computed properties:** Вычисляемые поля не хранятся, а рассчитываются на лету
- **Configuration:** Единый файл конфигурации вместо разбросанных параметров

### Связь с философией (⇑)

Онтология различия (α=+4): идентичность через уникальность, невозможность одновременного существования в двух местах.

### Реализация в коде (⇓)

```python
# card.py
@dataclass
class Card:
    id: str  # Уникальный ID — единственный источник истины
    linked_cards: List[str] = field(default_factory=list)  # Ссылки, а не копии!

    # ❌ ПЛОХО: хранить копию связанной карточки
    # linked_card_objects: List[Card] = []

    # ✅ ХОРОШО: хранить только ID, загружать при необходимости
    def get_linked_cards(self, manager: 'CardManager') -> List['Card']:
        return [manager.load(cid) for cid in self.linked_cards]
```

**Принципы (α=+1):** DRY (Don't Repeat Yourself), Normalization

## 3. Закон минимизации связности

### Формулировка

**Компоненты системы должны быть связаны друг с другом минимально необходимым образом.**

### Обоснование

Чем больше связей между компонентами, тем сложнее систему понять, изменить и тестировать. Каждая связь — это зависимость, которая ограничивает возможности изменения системы.

### Проявления

- **Low coupling:** Модули зависят друг от друга минимально
- **Dependency Injection:** Зависимости передаются извне, а не создаются внутри
- **Interface segregation:** Интерфейсы минимальны и специфичны
- **Event-driven:** Компоненты общаются через события, не зная друг о друге

### Связь с философией (⇑)

Принцип автономности (α=+3): каждая сущность должна быть способна существовать независимо.

### Реализация в коде (⇓)

```python
# card.py НЕ ЗАВИСИТ от card_manager.py
class Card:
    def to_markdown(self) -> str:
        # Логика сериализации — внутри Card
        pass

# card_manager.py зависит от card.py (односторонняя зависимость)
class CardManager:
    def save(self, card: Card):
        # Использует Card, но Card не знает о CardManager
        pass
```

**Принципы (α=+1):** Low Coupling, Dependency Inversion, Interface Segregation

## 4. Закон максимизации когезии

### Формулировка

**Элементы, которые изменяются вместе, должны находиться вместе.**

### Обоснование

Высокая когезия (cohesion) означает, что всё, что относится к одной ответственности, собрано в одном месте. Это упрощает понимание и изменение системы.

### Проявления

- **Single Responsibility:** Каждый класс отвечает за одну вещь
- **Feature folders:** Файлы группируются по фичам, а не по типам
- **Colocation:** Связанные файлы (компонент + стили + тесты) рядом
- **Domain-driven design:** Код организован по доменам бизнес-логики

### Связь с философией (⇑)

Принцип связности как источника смысла (α=+3): вещи обретают смысл через связь друг с другом.

### Реализация в коде (⇓)

```python
# ✅ ХОРОШО: Всё про карточку лекарства — в одном классе
@dataclass
class MedicineCard(Card):
    medication: dict = field(default_factory=dict)      # Данные о препарате
    administration: dict = field(default_factory=dict)   # Как принимать
    inventory: dict = field(default_factory=dict)        # Остаток

    def is_reorder_needed(self) -> bool:
        """Бизнес-логика проверки остатка — рядом с данными"""
        current = self.inventory.get('quantity_current', 0)
        reorder = self.inventory.get('reorder_level', 0)
        return current <= reorder
```

**Принципы (α=+1):** High Cohesion, Single Responsibility Principle

## 5. Закон обратимости операций

### Формулировка

**Критичные операции должны быть обратимы.**

### Обоснование

Люди совершают ошибки. Система должна позволять отменить критичные действия (удаление, изменение важных данных). Необратимость операций создаёт страх и снижает доверие к системе.

### Проявления

- **Undo/Redo:** Возможность отменить и повторить действия
- **Soft delete:** Удаление через флаг вместо физического удаления
- **Versioning:** История изменений (Git)
- **Confirmation:** Подтверждение перед критичными операциями

### Связь с философией (⇑)

Принцип доверия через предсказуемость (α=+3): система, которая позволяет исправить ошибки, вызывает доверие.

### Реализация в коде (⇓)

```python
# card_manager.py
def delete(self, card_id: str):
    """Удаление с возможностью восстановления"""
    file_path = self.cards_dir / f"{card_id}.md"
    if not file_path.exists():
        return

    # Soft delete: перемещение в .deleted вместо удаления
    deleted_dir = self.cards_dir / '.deleted'
    deleted_dir.mkdir(exist_ok=True)

    archive_path = deleted_dir / f"{card_id}.md"
    file_path.rename(archive_path)  # Можно восстановить!
```

**Принципы (α=+1):** Fail-Safe, User-Centered Design

## 6. Закон предсказуемости поведения

### Формулировка

**Одинаковые действия должны приводить к одинаковым результатам.**

### Обоснование

Непредсказуемость разрушает доверие к системе. Пользователь должен понимать, что произойдёт в результате его действий. Функции должны быть детерминированными и без побочных эффектов (где возможно).

### Проявления

- **Pure functions:** Функции без побочных эффектов
- **Immutability:** Неизменяемые данные
- **Idempotence:** Повторное выполнение даёт тот же результат
- **Explicit state:** Состояние явно передаётся в функции

### Связь с философией (⇑)

Принцип доверия (α=+3): предсказуемость создаёт доверие.

### Реализация в коде (⇓)

```python
# card.py
@staticmethod
def generate_id() -> str:
    """
    Детерминированная генерация ID

    НЕ детерминировано полностью (зависит от времени),
    но ПРЕДСКАЗУЕМО: всегда формат card_YYYYMMDD_HHMMSS_xxxx
    """
    now = datetime.datetime.now()
    timestamp = now.strftime("%Y%m%d_%H%M%S")
    random_suffix = secrets.token_hex(2)  # Случайность для уникальности
    return f"card_{timestamp}_{random_suffix}"

# ✅ ХОРОШО: Чистая функция
def filter_by_tag(cards: List[Card], tag: str) -> List[Card]:
    return [c for c in cards if tag in c.tags]

# ❌ ПЛОХО: Мутация аргумента
def add_tag(cards: List[Card], tag: str):
    for card in cards:
        card.tags.append(tag)  # Побочный эффект!
```

**Принципы (α=+1):** Pure Functions, Immutability, Idempotence

## 7. Закон градуального усложнения

### Формулировка

**Сложность системы должна нарастать постепенно, без резких скачков.**

### Обоснование

Система должна быть простой для простых случаев и сложной только тогда, когда это необходимо. Пользователь не должен сталкиваться со сложностью, пока она ему не нужна.

### Проявления

- **Progressive disclosure:** Скрытие сложности до момента, когда она нужна
- **Sensible defaults:** Разумные значения по умолчанию
- **Convention over configuration:** Соглашения вместо конфигурации
- **Layered API:** Простой API для простых задач, сложный для сложных

### Связь с философией (⇑)

Принцип простоты как результата сложности (α=+3): истинная простота достигается через осознанное управление сложностью.

### Реализация в коде (⇓)

```python
# cli.py — простой случай
# Минимальная команда: python cli.py create -t task --title "Купить хлеб"

# cli.py — сложный случай (все опции)
# python cli.py create -t task --title "..." --priority high --due 2026-01-25 --tags покупки,срочно

def create_card(self, args):
    # Defaults для простоты
    base_params = {
        'id': Card.generate_id(),
        'title': args.title,
        'created': datetime.datetime.now(),
        'modified': datetime.datetime.now(),
        'status': CardStatus.TODO,  # Default
        'priority': getattr(args, 'priority', CardPriority.MEDIUM),  # Default
        'tags': getattr(args, 'tags', '').split(',') if hasattr(args, 'tags') and args.tags else []
    }
```

**Принципы (α=+1):** KISS, Progressive Disclosure, Convention over Configuration

## 8. Закон композиционности

### Формулировка

**Сложные системы должны строиться из простых, независимых компонентов.**

### Обоснование

Монолитные системы трудно понять и изменить. Композиция простых компонентов позволяет создавать сложное поведение из понятных блоков.

### Проявления

- **Small functions:** Функции делают одну вещь хорошо
- **Composition over inheritance:** Композиция вместо наследования
- **Pipes and filters:** Unix philosophy (ls | grep | sort)
- **Microservices:** Малые независимые сервисы

### Связь с философией (⇑)

Онтология композиции (α=+4): целое — больше, чем сумма частей, но состоит из частей.

### Реализация в коде (⇓)

```python
# card_manager.py — композиция простых функций

def search(
    self,
    query: str = None,
    card_type: CardType = None,
    tags: List[str] = None,
    status: CardStatus = None,
    limit: int = 100
) -> List[Card]:
    """Сложный поиск = композиция простых фильтров"""
    all_cards = self._load_all_cards()

    # Каждый фильтр — простая функция
    if query:
        all_cards = self._filter_by_query(all_cards, query)
    if card_type:
        all_cards = self._filter_by_type(all_cards, card_type)
    if tags:
        all_cards = self._filter_by_tags(all_cards, tags)
    if status:
        all_cards = self._filter_by_status(all_cards, status)

    return all_cards[:limit]
```

**Принципы (α=+1):** Composition over Inheritance, Unix Philosophy, Small Functions

## 9. Закон локальности изменений

### Формулировка

**Изменения в системе должны быть локализованы в одном месте.**

### Обоснование

Когда одно изменение требует правок во многих местах кода, система становится хрупкой. Изменение одной функциональности должно затрагивать минимальное количество файлов.

### Проявления

- **Encapsulation:** Скрытие деталей реализации
- **Abstraction barriers:** Слои абстракции
- **Open/Closed:** Открыт для расширения, закрыт для изменения
- **Plugin architecture:** Добавление функций через плагины

### Связь с философией (⇑)

Принцип эволюции через использование (α=+3): система меняется, но изменения должны быть контролируемыми.

### Реализация в коде (⇓)

```python
# card.py — добавление нового типа карточки

# ✅ ХОРОШО: Достаточно добавить новый класс
@dataclass
class InvoiceCard(Card):
    """Новый тип карточки — счёт"""
    invoice_number: str = ""
    amount: float = 0.0

    # CardManager, CLI, visualizer работают БЕЗ ИЗМЕНЕНИЙ!

# Благодаря полиморфизму:
def save(self, card: Card):  # Принимает любой Card, включая InvoiceCard
    file_path = self.cards_dir / f"{card.id}.md"
    file_path.write_text(card.to_markdown())  # to_markdown() переопределён в InvoiceCard
```

**Принципы (α=+1):** Open/Closed Principle, Encapsulation, Liskov Substitution

## 10. Закон явности над неявностью

### Формулировка

**Явное лучше, чем неявное (Explicit is better than implicit).**

### Обоснование

Магия в коде затрудняет понимание. То, что происходит в системе, должно быть видно из кода. Явные зависимости, явные параметры, явные преобразования.

### Проявления

- **Explicit dependencies:** Зависимости передаются явно
- **Type hints:** Типы указываются явно (Python, TypeScript)
- **No magic:** Избегать магических констант, неявных преобразований
- **Clear naming:** Имена переменных говорят, что они содержат

### Связь с философией (⇑)

Принцип автономии через помощь (α=+3): пользователь должен понимать, что делает система.

### Реализация в коде (⇓)

```python
# card.py

# ✅ ХОРОШО: Явные типы
@dataclass
class Card:
    id: str
    type: CardType  # Enum, а не str!
    title: str
    created: datetime.datetime  # Явный тип даты
    tags: List[str] = field(default_factory=list)  # Явное значение по умолчанию

# ❌ ПЛОХО: Неявные типы
class Card:
    def __init__(self, id, type, title, created, tags=[]):  # Mutable default!
        self.id = id
        self.type = type  # Что это? str? int? Enum?
        self.created = created  # str? datetime? timestamp?

# ✅ ХОРОШО: Явная инъекция зависимости
class GraphVisualizer:
    def __init__(self, manager: CardManager):
        self.manager = manager  # Явно передаётся

# ❌ ПЛОХО: Неявная зависимость (глобальная переменная)
GLOBAL_MANAGER = CardManager()
class GraphVisualizer:
    def __init__(self):
        self.manager = GLOBAL_MANAGER  # Откуда она взялась?!
```

**Принципы (α=+1):** Explicit is better than implicit (Zen of Python), Type Safety

## 11. Закон устойчивости к ошибкам

### Формулировка

**Система должна сохранять работоспособность при ошибках.**

### Обоснование

Ошибки неизбежны: пользователи вводят некорректные данные, сеть падает, диск заполняется. Система должна обрабатывать ошибки gracefully, не падать и не терять данные.

### Проявления

- **Defensive programming:** Проверка входных данных
- **Error handling:** try/except, Result types, Option types
- **Graceful degradation:** Система работает с ограничениями при сбоях
- **Circuit breaker:** Предотвращение каскадных сбоев

### Связь с философией (⇑)

Принцип устойчивости через избыточность (α=+3): надёжность через множественность.

### Реализация в коде (⇓)

```python
# card_manager.py

def load(self, card_id: str) -> Optional[Card]:
    """Загрузка карточки с обработкой ошибок"""
    file_path = self.cards_dir / f"{card_id}.md"

    if not file_path.exists():
        # Нет файла — не ошибка, просто None
        return None

    try:
        content = file_path.read_text(encoding='utf-8')
        return Card.from_markdown(content)
    except (yaml.YAMLError, ValueError) as e:
        # Некорректный формат — логируем, возвращаем None
        print(f"⚠️  Ошибка загрузки {card_id}: {e}")
        return None
    except Exception as e:
        # Непредвиденная ошибка — логируем, но не падаем
        print(f"❌ Неожиданная ошибка при загрузке {card_id}: {e}")
        return None
```

**Принципы (α=+1):** Fail-Safe, Defensive Programming, Graceful Degradation

## 12. Закон измеримости качества

### Формулировка

**То, что нельзя измерить, нельзя улучшить.**

### Обоснование

Качество системы должно быть измеримо: производительность, надёжность, понятность кода. Без метрик невозможно понять, стала ли система лучше после изменений.

### Проявления

- **Code metrics:** Цикломатическая сложность, покрытие тестами
- **Performance monitoring:** Время отклика, throughput
- **Error tracking:** Количество ошибок, их типы
- **User metrics:** Время выполнения задач, количество ошибок пользователя

### Связь с философией (⇑)

Принцип красоты как критерия истины (α=+3): хороший код виден по метрикам.

### Реализация в коде (⇓)

```python
# demo.py — измеримые метрики

def demo_performance(manager: CardManager):
    """Демонстрация производительности"""
    import time

    # Создать 100 карточек
    start = time.time()
    for i in range(100):
        card = TaskCard(...)
        manager.save(card)
    save_time = time.time() - start

    # Поиск
    start = time.time()
    results = manager.search(query="лекарство")
    search_time = time.time() - start

    # Метрики
    print(f"📊 Метрики производительности:")
    print(f"   Сохранение 100 карточек: {save_time*1000:.0f} мс")
    print(f"   Поиск по 100 карточкам: {search_time*1000:.1f} мс")
    print(f"   Найдено результатов: {len(results)}")
```

**Принципы (α=+1):** Measurable Quality, Test-Driven Development, Observability

## Вертикальная трассировка

### ⇑ Связь с уровнями выше

**Философия применимости (α=+3):**
- Антропоцентричность → Закон предсказуемости (6)
- Простота как результат → Закон градуального усложнения (7)
- Время как измерение → Закон сохранения информации (1)
- Связность как смысл → Закон когезии (4)
- Память как идентичность → Закон единственности истины (2)
- Доверие через предсказуемость → Закон обратимости (5)
- Автономия через помощь → Закон явности (10)
- Устойчивость через избыточность → Закон устойчивости к ошибкам (11)
- Эволюция через использование → Закон локальности изменений (9)
- Красота как критерий → Закон измеримости (12)

**Онтология систем (α=+4):**
- Существование через различие → Закон единственности истины (2)
- Связь как основа бытия → Закон минимизации связности (3)
- Целое и части → Закон композиционности (8)

### ⇓ Связь с уровнями ниже

**Принципы и паттерны (α=+1):**
Каждый универсальный закон реализуется через несколько конкретных принципов:

1. **Сохранение информации** → Fail-Safe, Atomicity, Persistence
2. **Единственность истины** → DRY, SSOT, Normalization
3. **Минимизация связности** → Low Coupling, DI, Interface Segregation
4. **Максимизация когезии** → High Cohesion, SRP
5. **Обратимость** → Undo/Redo, Soft Delete, Versioning
6. **Предсказуемость** → Pure Functions, Immutability, Idempotence
7. **Градуальное усложнение** → KISS, Progressive Disclosure
8. **Композиционность** → Composition over Inheritance, Small Functions
9. **Локальность изменений** → Open/Closed, Encapsulation
10. **Явность** → Explicit is better than implicit, Type Safety
11. **Устойчивость** → Defensive Programming, Graceful Degradation
12. **Измеримость** → TDD, Code Metrics, Observability

**Код (α=-4):**
Все законы проявляются в конкретных реализациях в `card.py`, `card_manager.py`, `cli.py`, `demo.py`, `visualize_graph.py`.

## Применение законов

### Как использовать эти законы?

1. **При проектировании:** Проверьте каждое архитектурное решение на соответствие законам
2. **При код-ревью:** Используйте законы как чек-лист качества
3. **При рефакторинге:** Определите, какие законы нарушены, и исправьте
4. **При обучении:** Объясняйте принципы через универсальные законы

### Пример проверки дизайна

**Вопрос:** Нужно ли кэшировать результаты поиска карточек?

Проверка по законам:
- ✅ **Предсказуемость (6):** Кэш должен быть невидим пользователю (same input → same output)
- ⚠️ **Сохранение информации (1):** Кэш — это дублирование, нужна инвалидация
- ✅ **Измеримость (12):** Только если метрики показывают проблему производительности
- ⚠️ **Градуальное усложнение (7):** Добавлять кэш только когда без него медленно

**Решение:** Добавить LRU кэш с автоматической инвалидацией при изменении файлов (реализовано в `card_manager.py`).
