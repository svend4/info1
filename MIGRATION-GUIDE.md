# Migration Guide — Руководство по миграции на методологию ⇑⇓↔

**Версия:** 1.0
**Дата:** 2026-01-23
**Статус:** 📘 Практическое руководство
**CYCLE:** 20
**α-уровень:** +2 (методологический уровень)

---

## Введение

Это руководство поможет вам **постепенно** перевести существующий проект на методологию параллельного двунаправленного развития (⇑⇓↔). Миграция не требует переписывания проекта с нуля — методология **накладывается** на существующую структуру.

**Ключевая идея:** Вы не меняете код, вы меняете **способ мышления** о развитии проекта.

---

## Для кого это руководство?

✅ **Подходит для:**
- Действующих проектов с технической документацией
- Команд, желающих улучшить трассируемость требований
- Проектов с разрывом между архитектурой и реализацией
- Open-source проектов, где важна прозрачность развития

❌ **Не подходит для:**
- Проектов без документации (сначала создайте базовую документацию)
- Greenfield проектов (для них лучше применять методологию с самого начала)
- Проектов, где не планируется активное развитие

---

## Предварительные требования

Перед миграцией убедитесь, что у вас есть:

1. **Git-репозиторий** — вся история изменений
2. **Базовая документация** — хотя бы README.md
3. **Исходный код** — в любом состоянии
4. **2-4 часа времени** — для первого цикла миграции
5. **Python 3.8+** — для инструментов автоматизации

## Этапы миграции

### Этап 0: Подготовка (30 минут)

#### Шаг 1: Установка инструментов

```bash
# Клонировать репозиторий info1 (эталонный проект)
git clone https://github.com/svend4/info1.git /tmp/info1-tools

# Скопировать инструменты в ваш проект
cp -r /tmp/info1-tools/tools ./
cp /tmp/info1-tools/.github/workflows/metrics.yml ./.github/workflows/

# Убедиться, что Python 3.8+ установлен
python3 --version
```

#### Шаг 2: Первичный аудит

Запустите инструменты на вашем проекте:

```bash
# Рассчитать метрики здоровья
python3 tools/health_metrics.py

# Визуализировать связи
python3 tools/visualize_connections.py --format ascii
```

**Ожидаемый результат:** Инструменты обнаружат документы, но метрики будут низкими (это нормально!).

Запишите базовые метрики:
- CD (Connectivity Density): _______% (цель: 10-20%)
- VT (Vertical Traceability): _______% (цель: 50-70%)
- CR (Convergence Rate): _______ (цель: 0.7-1.5)
- DB (Directional Balance): _______% (цель: <30%)

### Этап 1: Маркировка существующих документов (1-2 часа)

#### Определите α-уровни

Пройдитесь по всем документам и присвойте им уровни абстракции:

```markdown
# Пример: README.md
**α-уровень:** +1 (общий обзор методологии)

# Пример: ARCHITECTURE.md
**α-уровень:** +1 (архитектурные решения)

# Пример: API.md
**α-уровень:** -1 (спецификация интерфейсов)

# Пример: src/main.py
**α-уровень:** -4 (реализация)
```

**Шкала уровней абстракции:**

| α-уровень | Название | Примеры документов |
|-----------|----------|-------------------|
| **+4** | Онтология/Философия | Vision, Philosophy, Principles |
| **+3** | Мета-методология | Development Process, Meta-docs |
| **+2** | Методология | Guidelines, Best Practices |
| **+1** | Концепции/Архитектура | Architecture, Design Docs, README |
| **0** | Спецификации (точка опоры) | Requirements, Specifications |
| **-1** | Интерфейсы | API Docs, Interfaces |
| **-2** | Примеры/Развертывание | Examples, Deployment |
| **-3** | Тесты | Unit tests, Integration tests |
| **-4** | Код | Source code |

#### Добавьте метаданные в документы

В начало каждого markdown-файла добавьте:

```markdown
**α-уровень:** [уровень]
**CYCLE:** [номер цикла, когда был создан/обновлен]
**Направление:** [⇑ / ⇓ / ↔]
```

**Пример:**

```markdown
# API Reference

**α-уровень:** -1
**CYCLE:** 1 (migration)
**Направление:** ⇓

Документация REST API системы...
```

### Этап 2: Первый цикл развития (2-3 часа)

Теперь примените методологию ⇑⇓↔ для **одного нового улучшения** проекта.

#### Структура цикла

**CYCLE 1 (migration):** Улучшение [название фичи/багфикса]

**⇑ ВВЕРХ (обобщение):**
- Что: Создать/обновить документ на уровне α≥0
- Почему: Объяснить **зачем** нужно это улучшение
- Пример: Обновить ARCHITECTURE.md с новым компонентом

**↔ СВЯЗИ (горизонтальное):**
- Что: Связать документы на одном уровне
- Почему: Показать **как** компоненты взаимодействуют
- Пример: Обновить README.md со ссылками на новые документы

**⇓ ВНИЗ (детализация):**
- Что: Создать/обновить код или низкоуровневые документы (α≤0)
- Почему: Реализовать **что конкретно** делает система
- Пример: Написать код новой фичи + unit-тесты

#### Пример первого цикла

**Задача:** Добавить аутентификацию в API

**⇑ ВВЕРХ:**
1. Обновить `ARCHITECTURE.md` (α=+1):
   ```markdown
   ## Компонент аутентификации

   **Добавлено:** CYCLE 1 (migration)

   Система использует JWT-токены для аутентификации...
   ```

**↔ СВЯЗИ:**
2. Обновить `README.md` (α=+1):
   ```markdown
   ## Безопасность

   Подробности аутентификации см. в [ARCHITECTURE.md](ARCHITECTURE.md#компонент-аутентификации)
   ```

**⇓ ВНИЗ:**
3. Создать `src/auth.py` (α=-4)
4. Создать `tests/test_auth.py` (α=-3)
5. Обновить `API.md` (α=-1) с новыми эндпоинтами

#### Коммит первого цикла

```bash
git add -A
git commit -m "CYCLE 1 (migration): Добавлена аутентификация

⇑ ВВЕРХ: Обновлена архитектурная документация
↔ СВЯЗИ: Добавлены ссылки в README
⇓ ВНИЗ: Реализован auth модуль + тесты
"
```

### Этап 3: Измерение прогресса (15 минут)

После первого цикла пересчитайте метрики:

```bash
python3 tools/health_metrics.py
```

**Что должно измениться:**
- CD (Connectivity Density): Небольшой рост (если добавили ссылки)
- VT (Vertical Traceability): Рост (если связали α-уровни)
- CR (Convergence Rate): Пока 1.0 (только один цикл)
- DB (Directional Balance): Зависит от баланса ⇑⇓↔

**Визуализация:**

```bash
# HTML визуализация
python3 tools/visualize_connections.py --format html --output graph.html
open graph.html  # посмотрите граф связей
```

### Этап 4: Регулярные циклы (ongoing)

#### Частота циклов

- **Малые проекты:** 1 цикл = 1-2 недели
- **Средние проекты:** 1 цикл = 1 неделя
- **Крупные проекты:** 1 цикл = 3-5 дней

#### Правило баланса

**Каждый цикл должен включать все три направления:**

| Направление | Минимум | Оптимально |
|-------------|---------|------------|
| ⇑ ВВЕРХ | 1 документ α≥0 создан/обновлен | 2-3 документа |
| ↔ СВЯЗИ | 2-3 новые ссылки между документами | 5-10 ссылок |
| ⇓ ВНИЗ | 1 модуль кода + тесты | 2-3 модуля |

#### Проверка баланса

После каждого цикла:

```bash
# Проверить DB (Directional Balance)
python3 tools/health_metrics.py --metric db

# Если DB > 30% — нужно балансировать направления
```

## Паттерны миграции для разных типов проектов

### Паттерн A: Web-приложение (React/Vue/Angular + Backend)

**Структура α-уровней:**

```
α=+2  ARCHITECTURE.md (общая архитектура)
α=+1  README.md, DESIGN.md
α=0   REQUIREMENTS.md
α=-1  API.md, COMPONENTS.md
α=-2  DEPLOYMENT.md, examples/
α=-3  tests/ (unit, integration, e2e)
α=-4  src/ (frontend + backend код)
```

**Первый цикл (рекомендация):**
- ⇑ Создать/обновить ARCHITECTURE.md
- ↔ Связать ARCHITECTURE ↔ API ↔ COMPONENTS
- ⇓ Добавить недостающие unit-тесты для критических компонентов

### Паттерн B: Библиотека/Framework

**Структура α-уровней:**

```
α=+3  PHILOSOPHY.md (философия дизайна)
α=+2  DESIGN-PRINCIPLES.md
α=+1  README.md, ARCHITECTURE.md
α=0   API-SPEC.md
α=-1  API-REFERENCE.md
α=-2  EXAMPLES.md, tutorials/
α=-3  tests/
α=-4  src/
```

**Первый цикл (рекомендация):**
- ⇑ Создать DESIGN-PRINCIPLES.md (почему библиотека спроектирована так)
- ↔ Связать примеры с API reference
- ⇓ Улучшить примеры использования

### Паттерн C: Микросервисная архитектура

**Структура α-уровней:**

```
α=+2  docs/ARCHITECTURE.md (общая архитектура)
α=+1  docs/SERVICE-OVERVIEW.md
α=0   docs/CONTRACTS.md (контракты между сервисами)
α=-1  service-*/API.md (для каждого сервиса)
α=-2  docker-compose.yml, k8s/
α=-3  service-*/tests/
α=-4  service-*/src/
```

**Первый цикл (рекомендация):**
- ⇑ Создать ARCHITECTURE.md с диаграммой всех сервисов
- ↔ Документировать контракты между сервисами (CONTRACTS.md)
- ⇓ Добавить интеграционные тесты для межсервисного взаимодействия

### Паттерн D: Data Science проект (ML/AI)

**Структура α-уровней:**

```
α=+3  RESEARCH-QUESTIONS.md (научные вопросы)
α=+2  METHODOLOGY.md (методология исследования)
α=+1  README.md, DATA-OVERVIEW.md
α=0   REQUIREMENTS.md (требования к модели)
α=-1  MODEL-SPEC.md (спецификация модели)
α=-2  notebooks/ (Jupyter notebooks с экспериментами)
α=-3  tests/ (валидация данных, метрики модели)
α=-4  src/ (preprocessing, training, inference)
```

**Первый цикл (рекомендация):**
- ⇑ Создать METHODOLOGY.md (объяснить подход к проблеме)
- ↔ Связать эксперименты (notebooks) с MODEL-SPEC
- ⇓ Добавить автоматические тесты метрик модели

## Частые проблемы и решения

### Проблема 1: "Метрики не рассчитываются"

**Симптомы:**
- CD = 0%, VT = 0%
- Инструменты не находят связи

**Решения:**
1. Проверьте, что добавили markdown-ссылки между документами:
   ```markdown
   См. [Архитектуру](ARCHITECTURE.md) для деталей
   ```

2. Убедитесь, что ссылки **относительные** (не HTTP):
   ```markdown
   ✅ [API](docs/API.md)
   ❌ [API](https://example.com/api)
   ```

3. Проверьте, что документы имеют расширение `.md`

### Проблема 2: "DB (Directional Balance) > 100%"

**Симптомы:**
- DB = 127% (как в проекте info1)
- Один из направлений доминирует

**Причина:** Неравномерное распределение документов по направлениям (⇑⇓↔)

**Решение:**
1. Посчитайте документы по направлениям:
   ```bash
   grep -r "Направление: ⇑" . | wc -l  # Сколько ⇑
   grep -r "Направление: ⇓" . | wc -l  # Сколько ⇓
   grep -r "Направление: ↔" . | wc -l  # Сколько ↔
   ```

2. В следующих циклах создавайте больше документов в недостающих направлениях

### Проблема 3: "VT (Vertical Traceability) низкий"

**Симптомы:**
- VT < 50%
- Нет связей между разными α-уровнями

**Решение:**
1. Добавьте **вертикальные ссылки** (|Δα| ≥ 2):
   ```markdown
   # В ARCHITECTURE.md (α=+1)
   Реализация см. в [src/main.py](../src/main.py) (α=-4)
   ```

2. Создайте **карту связей** (CONNECTION-MAP.md):
   ```markdown
   # Карта связей

   ## Архитектура → Код
   - [ARCHITECTURE.md](ARCHITECTURE.md) → [src/auth.py](src/auth.py)
   - [API.md](API.md) → [src/api/routes.py](src/api/routes.py)
   ```

### Проблема 4: "CR (Convergence Rate) нестабилен"

**Симптомы:**
- CR скачет (0.5 → 2.0 → 0.3)

**Причина:** Неравномерное количество документов в циклах

**Решение:**
1. Стабилизируйте ритм циклов (1 цикл = фиксированное время)
2. Стремитесь к 0.7-1.5 новых документов за цикл
3. Не создавайте все документы сразу — распределяйте по циклам

## Автоматизация миграции

### Скрипт первичной миграции

Создайте `migrate.sh` в корне проекта:

```bash
#!/bin/bash

echo "🚀 Миграция проекта на методологию ⇑⇓↔"
echo ""

# 1. Копировать инструменты
if [ ! -d "tools" ]; then
    echo "📦 Копирование инструментов..."
    cp -r /tmp/info1-tools/tools ./
fi

# 2. Первичный аудит
echo "📊 Рассчёт базовых метрик..."
python3 tools/health_metrics.py > baseline_metrics.txt
cat baseline_metrics.txt

# 3. Создать шаблон для CYCLE 1
echo ""
echo "📝 Создание шаблона CYCLE 1..."
cat > CYCLE-01-TEMPLATE.md <<'EOF'
# CYCLE 1 (migration): [Название улучшения]

**Дата:** $(date +%Y-%m-%d)

## ⇑ ВВЕРХ (обобщение)
- [ ] Создать/обновить документ на α≥0
- [ ] Объяснить "зачем" нужно улучшение

## ↔ СВЯЗИ (горизонтальное)
- [ ] Добавить ссылки между документами
- [ ] Обновить README/INDEX

## ⇓ ВНИЗ (детализация)
- [ ] Написать/обновить код
- [ ] Добавить тесты
- [ ] Обновить API docs (если нужно)

## Метрики до цикла
[Вставить из baseline_metrics.txt]

## Метрики после цикла
[Заполнить после завершения]
EOF

echo "✅ Миграция подготовлена!"
echo ""
echo "Следующие шаги:"
echo "1. Прочитайте CYCLE-01-TEMPLATE.md"
echo "2. Выполните первый цикл развития"
echo "3. Пересчитайте метрики: python3 tools/health_metrics.py"
```

### GitHub Actions для автоматической проверки

В `.github/workflows/metrics.yml` уже настроена автоматическая проверка метрик на каждый push/PR. После миграции она будет работать автоматически.

## FAQ

### Q: Нужно ли переписывать весь проект?

**A:** Нет! Методология **накладывается** на существующую структуру. Вы просто добавляете метаданные (α-уровни, направления) и улучшаете связи.

### Q: Сколько времени занимает миграция?

**A:**
- Первый цикл: 2-4 часа
- Стабилизация (5 циклов): 2-4 недели
- Полная адаптация (10 циклов): 2-3 месяца

### Q: Что если команда сопротивляется?

**A:**
1. Начните с небольшого эксперимента (1 цикл)
2. Покажите метрики "до/после"
3. Автоматизируйте максимум (CI/CD)
4. Не навязывайте — позвольте увидеть пользу

### Q: Можно ли применять частично (только ⇑ или только ⇓)?

**A:** Можно, но эффект будет ниже. Сила методологии — в **параллельном** развитии всех трёх направлений.

### Q: Как адаптировать для non-IT проектов?

**A:** Принципы универсальны! Примеры:
- Научное исследование: гипотезы (⇑) ↔ обзор литературы (↔) ↔ эксперименты (⇓)
- Бизнес-процессы: стратегия (⇑) ↔ процедуры (↔) ↔ инструкции (⇓)

## Заключение

Миграция на методологию ⇑⇓↔ — это **инвестиция** в будущее проекта. Через несколько циклов вы заметите:

✅ **Улучшенная трассируемость** — каждое требование связано с кодом
✅ **Быстрый onboarding** — новые разработчики понимают проект за дни, а не недели
✅ **Меньше технического долга** — методология заставляет думать на всех уровнях
✅ **Автоматический контроль качества** — метрики показывают проблемы до их критичности
