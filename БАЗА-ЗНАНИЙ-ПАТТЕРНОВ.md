## Часть I: Извлеченные уроки (Lessons Learned)

### 1.1. Метрики и измерения

#### ✅ УРОК 1: Адаптивные пороги важнее фиксированных

**Контекст:**
- Проект info1 - методологический проект (82.7% документов с α>0)
- Стандартный порог DB <30% показывал критическое состояние
- DB = 104.97% был "критичен", но это нормально для теоретического проекта

**Решение:**
- Создан тип проекта "methodology" с адаптированными порогами
- DB target: <30% → <132% (учитывает теоретическую природу)
- VT target: 50-70% → 22-44% (фокус на философии)

**Принцип:**
> Не подстраивайте проект под метрики, подстраивайте метрики под тип проекта.

**Применимость:**
- ✅ Методологические проекты (высокая теория, низкий код)
- ✅ Библиотеки (высокая VT, низкая CD)
- ✅ Data Science проекты (низкая VT, высокая экспериментация)
- ✅ Любые проекты с нестандартной структурой

**Анти-паттерн:**
- ❌ Использовать одинаковые пороги для всех проектов
- ❌ Считать метрику "плохой" без понимания контекста

#### ✅ УРОК 2: Семантика важнее синтаксиса при анализе

**Контекст:**
- Функция `_extract_direction()` определяла направление по текстовому поиску ⇑⇓↔
- Все документы содержали ⇑ в упоминании "методология ⇑⇓↔"
- Результат: 100% документов помечены как ⇑ UP (неправильно)

**Решение:**
- Изменена логика на основе **уровня абстракции α**:
  ```python
  if alpha > 0:  # Философия, теория
      return 'up'
  elif alpha < 0:  # Код, примеры
      return 'down'
  else:  # Архитектура
      return 'horizontal'
  ```

**Принцип:**
> Анализируйте семантику (что документ делает), а не синтаксис (что в нем написано).

**Применимость:**
- ✅ Анализ направлений развития (⇑⇓↔)
- ✅ Классификация документов
- ✅ Определение ролей компонентов
- ✅ Любой NLP/text mining

**Анти-паттерн:**
- ❌ Полагаться только на keyword matching
- ❌ Игнорировать контекст и структуру

### 2.2. Паттерн: Регулярное сохранение метрик

**Проблема:**

- Нет истории для анализа трендов
- Невозможно предсказать проблемы

**Применимость:**

### 2.3. Паттерн: Приоритизация улучшений

**Проблема:**
- Много проблем одновременно
- Непонятно, с чего начать
- Ограниченные ресурсы

**Решение (self_improvement.py):**
```python
def prioritize_recommendations(problems):
    for problem in problems:
        severity = calculate_severity(problem)  # CRITICAL/HIGH/MEDIUM/LOW
        impact = estimate_impact(problem)  # % улучшения метрики
        effort = estimate_effort(problem)  # сложность
        priority = (severity * impact) / effort
    return sorted_by_priority
```

**Критерии приоритизации:**
1. **Severity:** Насколько критична проблема?
2. **Impact:** Насколько улучшится метрика?
3. **Effort:** Сколько времени потребуется?
4. **Dependencies:** Блокирует ли другие задачи?

**Пример:**
```
ПРИОРИТЕТ 1 [CRITICAL]: Исправить DB
  - Severity: CRITICAL (DB=141%, target <30%)
  - Impact: -111% к DB
  - Effort: MEDIUM (нужно исправить логику)
  - Priority: (9 * 111) / 5 = 199.8

ПРИОРИТЕТ 4 [LOW]: Добавить маркеры α в код
  - Severity: LOW
  - Impact: +5% к VT
  - Effort: HIGH (нужно обновить весь код)
  - Priority: (2 * 5) / 8 = 1.25
```

### 2.4. Паттерн: Итеративное улучшение с обратной связью

**Процесс:**
```
1. Измерить (health_metrics.py)
       ↓
2. Диагностировать (self_improvement.py)
       ↓
3. Приоритизировать
       ↓
4. Действовать (выполнить #1 приоритет)
       ↓
5. Измерить снова
       ↓
6. Проверить улучшение
       ↓
7. Сохранить в историю (save_metrics.py)
       ↓
8. Повторить
```

**Ключевые принципы:**
- ✅ Делать по одному приоритету за раз
- ✅ Измерять до и после
- ✅ Проверять ожидаемый vs фактический эффект
- ✅ Откатывать, если эффект отрицательный
- ✅ Документировать результаты

**Анти-паттерн:**
- ❌ Делать много изменений сразу (непонятно, что сработало)
- ❌ Не измерять результат
- ❌ Игнорировать отрицательные эффекты

## Часть III: Антипаттерны (что НЕ работает)

### ❌ АНТИПАТТЕРН 1: Догматичные метрики

**Описание:**
Использовать фиксированные пороги для всех проектов без учета контекста.

**Почему не работает:**
- Методологический проект != веб-приложение != библиотека
- DB=105% критично для webapp, но нормально для methodology project
- VT=30% низко для library, но оптимально для theory-focused project

**Последствия:**
- Ложные тревоги
- Потеря доверия к метрикам
- Бессмысленная работа по "исправлению" несуществующих проблем

**Правильный подход:**
Использовать адаптивные пороги (adaptive_metrics.py).

---

### ❌ АНТИПАТТЕРН 2: Метрики ради метрик

**Описание:**
Измерять все подряд без понимания зачем и что делать с результатами.

**Примеры:**
- Измерять code coverage, но не использовать для улучшения тестов
- Считать LOC (lines of code), но не анализировать качество
- Собирать performance metrics, но не оптимизировать

**Почему не работает:**
- Метрики без действий = потерянное время
- Data hoarding без insights
- Cognitive overload от избытка информации

**Правильный подход:**
- Измеряйте только actionable metrics
- Для каждой метрики: "Что я буду делать, если она плохая?"
- Меньше метрик, больше действий

---

### ❌ АНТИПАТТЕРН 3: Связи ради связей

**Описание:**
Добавлять максимум связей между документами, думая что "больше = лучше".

**Пример:**
Секция "См. также" с 30+ ссылками.

**Почему не работает:**
- Информационная перегрузка
- Невозможно определить действительно важные связи
- Снижается полезность навигации

**Показатель проблемы:**
CD > 50% (избыточная связность).

**Правильный подход:**
- Максимум 15 связей на документ
- Разделить на "Основные" (3-5) и "Дополнительные"
- Приоритет вертикальным связям (⇑⇓)

---

### ❌ АНТИПАТТЕРН 4: Текстовый поиск вместо семантического анализа

**Описание:**
Определять свойства документа по наличию ключевых слов.

**Пример из info1:**
```python
# Плохо
if '⇑' in content:
    return 'up'  # Все документы с "⇑⇓↔" помечаются как UP
```

**Почему не работает:**
- Контекст важнее ключевых слов
- Символы могут быть в цитатах, примерах, заголовках

**Правильный подход:**
```python
# Хорошо
if alpha > 0:  # Семантический анализ уровня
    return 'up'
```

### 4.3. Частые вопросы от новых проектов

**Q: С чего начать?**
A: С философии (α=+3). Ответьте: "Почему этот проект существует?" Затем двигайтесь ⇓ вниз к коду.

**Q: Сколько документов нужно?**
A: Минимум 9 (по одному на каждый уровень α). Оптимум: 20-50 для medium project.

**Q: Мои метрики "плохие", что делать?**
A:
1. Проверьте тип проекта (adaptive_metrics.py)
2. Запустите self_improvement.py
3. Выполните приоритет #1
4. Не паникуйте — улучшение итеративное

**Q: Нужно ли создавать все 9 уровней α?**
A: Нет. Для практических проектов достаточно 5-7 уровней. α=+4 (онтология) опционален.

**Q: Как часто измерять метрики?**
A: Минимум после каждого значимого коммита. Идеал: в CI/CD pipeline.

```json
{
  "lesson": {
    "id": "lesson_001",
    "title": "Адаптивные пороги важнее фиксированных",
    "category": "metrics",
    "severity": "high",
    "context": {
      "project_type": "methodology",
      "problem": "DB=104% показывал критическое состояние",
      "solution": "Адаптировать порог под тип проекта"
    },
    "principle": "Не подстраивайте проект под метрики, подстраивайте метрики под проект",
    "applicability": ["methodology", "library", "datascience"],
    "evidence": {
      "before": {"db": 141.42, "status": "critical"},
      "after": {"db": 104.97, "status": "good"}
    },

  }
}
```
