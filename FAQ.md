## 🔵 Методология ⇑⇓↔

### Q: Что такое ⇑⇓↔?

**A:** Это методология параллельного двунаправленного развития, где каждый цикл включает работу в **трёх направлениях одновременно**:

- **⇑ ВВЕРХ (обобщение)** — переход к более высоким уровням абстракции
- **⇓ ВНИЗ (детализация)** — конкретизация и реализация
- **↔ СВЯЗИ (горизонтальные)** — связи между элементами одного уровня

**Ключевое отличие** от традиционных подходов: все три направления развиваются **параллельно**, а не последовательно.

**См. также:** [ДОКУМЕНТАЦИЯ.md](ДОКУМЕНТАЦИЯ.md) для полного описания.

---

### Q: Зачем нужно развиваться в трёх направлениях одновременно?

**A:** Параллельное развитие даёт несколько преимуществ:

1. **Баланс:** Избегаете ситуации "только теория" или "только код"
2. **Связность:** Каждый новый элемент связан с другими частями системы
3. **Целостность:** Система развивается гармонично на всех уровнях
4. **Проверяемость:** Теория немедленно проверяется практикой, и наоборот

**Пример:**
```
Плохо (последовательно):
1. Написать всю теорию (⇑)
2. Потом написать весь код (⇓)
3. Потом связать (↔)

Хорошо (параллельно):
ЦИКЛ 1: Теория + Код + Связи для фичи A
ЦИКЛ 2: Теория + Код + Связи для фичи B
...
```

### Q: Что такое α-уровни?

**A:** α-уровни — это **9 уровней абстракции** от конкретного кода до философии:

| Уровень | Описание | Пример |
|---------|----------|--------|
| **α=+4** | Философия/Онтология | Природа знания |
| **α=+3** | Теория | Формальные модели |
| **α=+2** | Методология | Процессы и практики |
| **α=+1** | Концепция/Дизайн | Архитектурные решения |
| **α=0** | Архитектура | Структура системы |
| **α=-1** | Руководства | How-to guides |
| **α=-2** | Детальная документация | API reference |
| **α=-3** | Примеры/Тесты | Конкретные примеры кода |
| **α=-4** | Конкретный код | Реализация |

**Зачем это нужно?** Чтобы измерить вертикальную трассируемость (VT) — насколько хорошо связаны разные уровни абстракции.

### Q: Как определить направление документа?

**A:** Задайте себе вопрос: "Что делает этот документ?"

- **⇑ ВВЕРХ:** Обобщает, абстрагирует, выводит паттерны, создаёт теорию
  - Примеры: методологии, философия, онтология, мета-анализ
- **⇓ ВНИЗ:** Детализирует, конкретизирует, показывает "как"
  - Примеры: руководства, примеры, code snippets, troubleshooting
- **↔ СВЯЗИ:** Связывает, навигирует, интегрирует
  - Примеры: карты, индексы, обзоры, интеграционные документы

**Правило большого пальца:** Если сомневаетесь между ⇑ и ⇓, спросите: "Это ближе к 'почему' (⇑) или 'как' (⇓)?"

### Q: Сколько времени занимает один цикл?

**A:** Зависит от масштаба задачи:

- **Маленькая фича:** 2-4 часа
- **Средняя фича:** 1-2 дня
- **Крупная фича:** 3-5 дней

**Важно:** Не время определяет цикл, а **завершённость** — цикл считается завершённым, когда созданы документы во всех трёх направлениях (⇑⇓↔).

**Рекомендация:** Начинайте с малых циклов (2-4 часа), чтобы почувствовать ритм.

---

### Q: Обязательно ли создавать новые файлы в каждом направлении?

**A:** Нет. Можно:

1. **Создать новый файл** (например, новое руководство)
2. **Обновить существующий файл** (добавить раздел к документации)
3. **Добавить связи** между существующими файлами

**Главное:** В конце цикла должен быть **прогресс во всех трёх направлениях**, даже если это 1 параграф в ⇑, 10 строк кода в ⇓, и 2 ссылки в ↔.

## 📊 Инструменты и метрики

### Q: Что измеряют метрики CD, VT, CR, DB?

**A:** Четыре ключевые метрики здоровья проекта:

| Метрика | Что измеряет | Целевой диапазон | Как улучшить |
|---------|--------------|------------------|--------------|
| **CD** (Connectivity Density) | Плотность связей между документами | 10-20% | Добавить/убрать связи |
| **VT** (Vertical Traceability) | % вертикальных связей (между уровнями) | 50-70% | Связать философию↔код |
| **CR** (Convergence Rate) | Сходимость к высоким уровням | 0.7-1.5 | Создавать high-level docs |
| **DB** (Directional Balance) | Баланс направлений ⇑⇓↔ | <30% | Создавать ⇓↔ документы |

**Приоритет:** DB > VT > CD > CR

**См. также:** [МЕТРИКИ-ЗДОРОВЬЯ.md](МЕТРИКИ-ЗДОРОВЬЯ.md) для деталей.

---

### Q: Мои метрики "плохие" — что делать?

**A:** Не паникуйте. Используйте dashboard для приоритизации:

```bash
python3 tools/dashboard.py --recommendations
```

Dashboard покажет проблемы в порядке важности:
- 🔴 **CRITICAL** — исправить немедленно
- ⚠️ **HIGH** — исправить в ближайшие 1-2 цикла
- 🟡 **MEDIUM** — исправить когда удобно
- 🟢 **LOW** — косметические улучшения

**Стратегия:**
1. Исправьте 1-2 CRITICAL проблемы в следующем цикле
2. Не пытайтесь исправить всё сразу
3. Метрики улучшаются постепенно (10-20 циклов)

### Q: Что такое anti-паттерны и почему их так много?

**A:** Anti-паттерны — это **структурные проблемы** в проекте:

1. **Orphan Documents** — документы без связей вообще
2. **Dead Ends** — документы без исходящих ссылок
3. **Hub Documents** — документы с >20 связями
4. **Missing α-level** — документы без уровня абстракции
5. **Unbalanced Directions** — один направление доминирует
6. **Empty Cycles** — пропущенные номера циклов
7. **Isolated Clusters** — низкий уровень не связан с высоким

**Почему много?** В начале проекта anti-паттерны нормальны. По мере развития их количество снижается.

**Что делать?** Фокусируйтесь на CRITICAL и HIGH severity. MEDIUM и LOW можно игнорировать.

## 🚀 Применение на практике

### Q: С чего начать применение методологии?

**A:** Следуйте 3-шаговому плану:

**Шаг 1: Quick Start (5 минут)**
```bash
# Скопируйте инструменты
cp -r info1/tools/ your-project/tools/

# Запустите dashboard
python3 tools/dashboard.py --quick
```

**Шаг 2: Первый цикл (2-4 часа)**
- Выберите небольшую задачу
- Создайте 3 документа (⇑⇓↔) или обновите существующие
- Добавьте метаданные (α-уровень, направление, цикл)

**Шаг 3: Измерение (5 минут)**
```bash
python3 tools/dashboard.py --recommendations
```

**См. также:** [QUICK-START.md](QUICK-START.md) для пошаговой инструкции.

### Q: Можно ли применить к существующему проекту?

**A:** Да! Используйте постепенную миграцию:

**Этап 0:** Установка инструментов (30 минут)
**Этап 1:** Маркировка 5-10 ключевых документов метаданными (1-2 часа)
**Этап 2:** Первый цикл ⇑⇓↔ для нового улучшения (2-3 часа)
**Этап 3:** Измерение прогресса (15 минут)
**Этап 4:** Регулярные циклы (ongoing)

**Важно:** Не нужно переписывать весь проект. Новые изменения делайте по методологии, старые трогайте по мере необходимости.

**См. также:** [MIGRATION-GUIDE.md](MIGRATION-GUIDE.md) для детального плана.

### Q: Как работать в команде с методологией ⇑⇓↔?

**A:** Рекомендации для команд:

1. **Синхронизация циклов:**
   - Команда работает в одном цикле одновременно
   - Каждый член делает свою часть ⇑⇓↔
   - Цикл завершается коллективно

2. **Code review:**
   - Проверяйте наличие всех трёх направлений
   - Проверяйте метаданные (α-уровень, направление, цикл)
   - Запускайте CI/CD с метриками

3. **Ритм:**
   - Устан��вите частоту циклов (например, 1 цикл = 1 спринт)
   - Синхронизируйте с другими процессами (Scrum, Kanban)

4. **Dashboard:**
   - Ежедневный stand-up: обсуждайте метрики
   - Ретроспектива: анализируйте anti-паттерны

### Q: Совместима ли методология с Agile/Scrum?

**A:** Да, отлично совместима:

| Scrum | ⇑⇓↔ |
|-------|------|
| Sprint | Cycle |
| Sprint Goal | Задача цикла |
| Sprint Planning | Планирование направлений ⇑⇓↔ |
| Daily Standup | Обсуждение прогресса в направлениях |
| Sprint Review | Демонстрация результатов цикла |
| Sprint Retro | Анализ метрик и anti-паттернов |

**Пример интеграции:**
- 1 Sprint = 2-3 Cycles (если спринт 2 недели, цикл 3-5 дней)
- Каждый цикл включает ⇑⇓↔ для своей фичи
- CI/CD проверяет метрики при каждом PR

## 🔄 Миграция существующих проектов

### Q: Сколько времени занимает миграция?

**A:** Зависит от размера проекта:

| Размер проекта | Этап 1 (маркировка) | Этап 2 (первый цикл) | Этап 3 (измерение) | Итого |
|----------------|---------------------|----------------------|--------------------|-------|
| Маленький (<20 docs) | 30 мин | 1-2 часа | 15 мин | **2-3 часа** |
| Средний (20-100 docs) | 1-2 часа | 2-3 часа | 15 мин | **4-6 часов** |
| Крупный (>100 docs) | 2-4 часа | 3-5 часов | 30 мин | **6-10 часов** |

**Важно:** Это единоразовая инвестиция. После миграции работа идёт естественным образом.

### Q: После миграции DB > 100% — это нормально?

**A:** Да, это **ожидаемо** для проектов с большой существующей документацией.

**Причина:** Большинство существующих документов — это ⇑ ВВЕРХ (теория, архитектура). Практических руководств (⇓) и связей (↔) мало.

**Решение:** Следующие 5-10 циклов создавайте только ⇓ и ↔ документы. DB будет постепенно снижаться.

**Пример:**
```
После миграции: DB=150%, 90%⇑ / 5%⇓ / 5%↔
Через 5 циклов:  DB=100%, 70%⇑ / 15%⇓ / 15%↔
Через 10 циклов: DB=50%,  50%⇑ / 25%⇓ / 25%↔
Через 20 циклов: DB=20%,  40%⇑ / 30%⇓ / 30%↔  ← Идеал
```

## ⚙️ CI/CD и автоматизация

### Q: Нужен ли CI/CD для использования методологии?

**A:** Нет, но **настоятельно рекомендуется**.

**Без CI/CD:**
- Вы запускаете инструменты вручную
- Легко забыть проверить метрики
- Нет истории метрик

**С CI/CD:**
- ✅ Автоматическая проверка при каждом коммите
- ✅ PR комментарии с метриками
- ✅ История метрик во времени
- ✅ Визуализации в артефактах

**Настройка занимает 15-20 минут.** См. [SETUP-CI-CD.md](SETUP-CI-CD.md).

---

### Q: Какой CI/CD платформу выбрать?

**A:** Рекомендации:

1. **GitHub Actions** — лучший выбор, если используете GitHub
   - Простая настройка
   - Бесплатно для публичных репозиториев
   - 2000 минут/месяц для приватных

2. **GitLab CI** — если используете GitLab
   - Встроен в GitLab
   - Unlimited minutes для self-hosted runners

3. **Локальные pre-commit hooks** — минимальный вариант
   - Не требует cloud CI/CD
   - Работает локально

**См. также:** [SETUP-CI-CD.md](SETUP-CI-CD.md) для конфигураций всех вариантов.

---

### Q: Workflow падает с "Permission denied" — что делать?

**A:** Добавьте permissions в workflow:

```yaml
jobs:
  calculate-metrics:
    permissions:
      contents: write  # Для push в metrics-history
      pull-requests: write  # Для PR комментариев
    runs-on: ubuntu-latest
    # ... остальное
```

**См. также:** [TROUBLESHOOTING.md#проблема-13](TROUBLESHOOTING.md#проблема-13) для деталей.

### Q: Можно ли использовать методологию для non-code проектов?

**A:** Да! Методология универсальна:

- **Исследования:** Теория (⇑) + Эксперименты (⇓) + Связи между областями (↔)
- **Обучение:** Концепции (⇑) + Упражнения (⇓) + Связи между темами (↔)
- **Продуктовая разработка:** Vision (⇑) + Features (⇓) + User journey (↔)
- **Бизнес-процессы:** Стратегия (⇑) + Операции (⇓) + Интеграция (↔)

**Главное:** Наличие **разных уровней абстракции** и **необходимость связывать их**.

---

### Q: Есть ли альтернативы методологии ⇑⇓↔?

**A:** Похожие подходы:

- **Zettelkasten** — похоже на ↔ (связи), но нет ⇑⇓
- **Top-Down / Bottom-Up** — похоже на ⇑⇓, но последовательно, не параллельно
- **Living Documentation** — похоже на связь код↔документация
- **Model-Driven Architecture** — похоже на уровни абстракции (α)

**Отличие ⇑⇓↔:** Единственная методология с **параллельным** развитием в **трёх** направлениях + **измеримые метрики**.

---

### Q: Методология подходит только для больших проектов?

**A:** Нет, методология масштабируется:

**Маленькие проекты (<10 документов):**
- Минимальные циклы (1-2 часа)
- Неформальные метаданные
- Ручной запуск dashboard раз в неделю

**Средние проекты (10-100 документов):**
- Регулярные циклы (3-5 дней)
- Метаданные в ключевых документах
- CI/CD с метриками

**Крупные проекты (>100 документов):**
- Строгие циклы с командной синхронизацией
- Метаданные везде
- CI/CD + history tracking + ретроспективы

**Начните с минимального, масштабируйте по мере роста.**
